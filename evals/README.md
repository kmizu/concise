# Response evaluations

This suite checks whether concise preserves useful answers while reducing
unnecessary text. It covers simple facts, complex short questions, uncertainty,
authorized work, blocking questions, destructive cleanup, repeated failures,
multiple requested topics, and explanations, in English and Japanese.

`cases.json` contains the prompts and semantic rubrics. `prompts.json` is the
same input without rubrics, for the answer-generating agent. The actual captured
answers, rule snapshots, blinded review, and [pilot report](PILOT.md) are checked
in so the result can be inspected without model access.

## What counts as success

An independent reviewer judges each answer for accuracy, completeness,
readability, and unnecessary questions. A quality pass requires the first three
to be true and unnecessary questions to be false. Evidence must identify what
the answer did well or omitted. Required clarification is not a failure.

Character counts and line counts are separate measurements. A shorter wrong or
incomplete answer fails. Only simple facts have a length target, and that target
does not override semantic quality. Regex checks are content indicators only:
`Not Canberra` matches the capital indicator but is still wrong.

## Run a new comparison

1. Copy the suite and prompt-only input into a new directory inside `evals/`.
   Freeze rule snapshots before collection. Create one fresh agent context per
   condition, with identical model settings and common harness instructions.
   Provide only the prompt-only input and that condition's rules, or no concise
   rules. For a stronger study, use fresh sessions for every case and repeated
   samples, recorded as separate experiments.
2. Capture answers without editing them as JSON arrays of `{case_id, text}`.
   These are fictional text-only scenarios: do not execute their deployments,
   fixes, cleanup, or other actions. Record date, model identity/settings when
   exposed, collection method, sample count, and limitations.
3. Create an experiment manifest following `pilot.json`: `cases_file`,
   `cases_sha256`, `collection`, and `conditions`. Each condition names its
   `answers_file`, optional `rules_file`, and `rules_sha256`. Paths are relative
   to the manifest's directory and stay inside it. Hash UTF-8 text with LF
   newlines using `text_hash` in `scripts/evaluate_responses.py`.
4. Prepare anonymized answers. Labels are shuffled independently per case.
   Give a fresh reviewer only `review-input.json`; keep condition names, rules,
   generator history, and `review-key.json` hidden until review is complete.

   ```bash
   python scripts/prepare_response_review.py evals/pilot.json
   ```

5. Ask the reviewer to write a JSON object with `reviewer` provenance,
   `review_input_sha256`, and a `reviews` array. The reviewer independently
   hashes the exact UTF-8 `review-input.json` text with CRLF normalized to LF.
   The input includes an opaque source fingerprint to bind its case and rule
   versions without revealing condition names. Each entry needs `case_id`, `variant`, the four boolean
   decisions `accurate`, `complete`, `readable`, `unnecessary_question`, and
   specific `evidence`. See `blind-decisions.json` for the recorded example.
   Attach the decisions, then set `reviews_file: "reviews.json"` in each
   manifest condition.

   ```bash
   python scripts/prepare_response_review.py evals/pilot.json --attach evals/blind-decisions.json
   ```

6. Score quality and length separately. Gate only the candidate if an older
   baseline intentionally includes failures; omitting `--condition` gates all
   conditions. `--require-quality` exits 1 for failed or unreviewed answers;
   invalid or stale inputs exit 2.

   ```bash
   python scripts/evaluate_responses.py evals/pilot.json --output evals/results.json --require-quality --condition revised
   ```

The scripts run offline with the Python standard library. They check case
coverage, source hashes, reviewer provenance, boolean decisions, and answer
hashes. Attaching checks the hash of the actual reviewed input; scoring checks
the review-time source fingerprint. Old decisions cannot be attached after
regenerating a key for changed answers, cases, or rules. These scripts do not call a model or establish that a reviewer's judgment is
correct. CI rechecks recorded decisions, not fresh model behavior. Changing the
rules requires a fresh capture and review, not editing a previous grade.

## Scope of the pilot

The pilot uses one batch of twelve answers per condition, generated by fresh
Codex agents sharing the session's inherited model settings. Its independent
reviewer is another agent from the same model family. Condition labels were
hidden, but stylistic clues may still reveal them. Shared harness instructions
also influence the no-rules condition.

These are not repeated trials, native Claude Code model responses, actual
multi-turn work, or a persistence test. The results can expose omissions and
support a wording change; they do not establish statistical significance or
general improvement across models and tasks.
